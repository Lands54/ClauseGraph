# 三路算法

三路共用同一份条款底图。一路建立条款之间的有向检索关系。二路把条款挂到项目预定义的类型概念。三路从每份文档中抽取内容概念和关系，并记录关联条款。

## 一路 · BM25

1. 提取条款标题、直属正文和表格文本，做 Unicode NFKC 规范化和大小写折叠。连续汉字按相邻双字切分，单字和其他词项直接保留。
2. 把选定语料写入内存 SQLite FTS5。每个条款以自身去重后的词项做 OR 查询，排除自身。候选可来自同一份或不同文档。
3. 按 FTS5 原始 BM25 分数升序排列，分数相同按条款 ID 排序。输出有向 `SIMILAR_TO`，记录排名、匹配词项和两端原文证据。

项目快照默认保存全部有词项命中的边。快照生成、批处理和独立构建均可显式限制每个条款写入的出向边数。工作台的全图 Top K 作用于查询，对每个源条款保留排名前 K 的 BM25 边，并返回其他关系和全部节点。BM25 分数依赖语料范围，换一组文件生成快照时分数和排序可能变化。

## 二路 · 预定义本体与规则挂接

1. 加载 Turtle 本体中的概念、关系和匹配规则，生成 `TypeConcept` 和 `TYPE_RELATION`。若规则指定了文档类型，只匹配该类型。
2. 对条款检查标题、正文、表格首行和编号正则。每个命中组只加一次权重，分数上限为 1。标题、正文、表头、编号的默认权重分别为 0.40、0.20、0.35、0.20。
3. 达到概念阈值才产生 `CLASSIFIED_AS`，默认阈值为 0.40。确认还需达到本体的确认阈值和最少证据组数，默认分别为 0.72 和 2 组。其余已挂接结果标为 `review_required`。证据保留命中的原文位置，未匹配条款记录在路线元数据中。

两个文档的条款可以通过共享类型概念，或通过类型概念之间已有的本体关系形成查询路径。

## 三路 · 内容本体与条款挂接

1. 将同一文档的标题、直属段落与表格行按条款顺序拼接，在每个条款前添加 `[clause_id=…]`，再把整份文本交给 OntoRAG。
2. 外部模型在术语抽取请求中同时返回术语和 `mentions`，每条挂接只需返回概念及条款 ID。OntoRAG 学习流程内部还可为术语分类、层级和关系抽取发出多次请求。
3. 引擎验证输出结构和条款 ID。有效挂接按条款与概念去重，无效 ID 记入 `unresolved_mentions`。概念身份包含文档版本，同名概念可在不同文档各自存在。
4. 引擎用条款的首个非空来源块作为回查位置，并标记 `pending`。这是条款定位，关联是否语义成立仍需复核。概念关系使用有效引文或端点挂接作为证据，也标记 `pending`。

三路默认关闭，可按运行或文件导入启用。适配器会在上游提示缺少全文时补齐输入。模型服务的上下文和响应长度仍有上限。请求、结构或引文校验失败按文档记录。有效但无法解析的挂接候选与整份文档抽取失败分开统计。
